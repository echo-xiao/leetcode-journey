# Kerno 果核 · 设计系统

> 2026-11-17 · 对应设计稿 `docs/design/leet-jounry-ui.html`
>
> 这份文档定义**数值和它们的名字**。组件长什么样看设计稿，为什么是这个数看这里。
> 两份不一致时，以这份为准——设计稿是实现，这份是规格。

---

## 0. 怎么用这份文档

### 三层结构

```
1  基元 (primitives)    原始值：色号、字号、间距数字
      ↓  只被第 2 层引用。产品代码永远不碰这一层
2  语义 (semantic)      --ink-2  --t-body  --accent  --s4
      ↓  产品代码只认这一层
3  组件 (components)    Row / Card / Button / Flag
```

### 铁律

**产品代码里不准出现裸值。** 看见 `#30CF79`、`font-size: 13px`、`padding: 16px`
就是漏了一层。唯一的例外是第 1 层自己的定义处。

这条不是洁癖。整个系统的价值就在于"改一处，全局跟着变"——只要有一个裸值，
它就会在下次改版时留在原地，变成一个没人记得为什么长这样的异类。文件里
现在那几个 `13.5px` / `11.5px` 就是这么来的。

### 命名约定

| 前缀 | 含义 | 例 |
|---|---|---|
| `--t-*` | type，字号 | `--t-body` |
| `--lh-*` | line-height，行高 | `--lh-body` |
| `--w-*` | weight，字重 | `--w-semi` |
| `--ink-*` | 文字色，数字越大越淡 | `--ink-2` |
| `--s*` | space，间距 | `--s4` |
| `--r*` | radius，圆角 | `--r3` |

语义名说的是**用途**不是外观。`--ink-3` 是"第三层文字"，不是"灰色"——
换深色模式时它自己会变成浅灰，名字不用改。`--gray-500` 就得全文替换。

## 1. 两个平台，一套系统

Chrome 侧边栏和 iOS app 是同一个产品，但**不共用数值**。

| 一份，改一处两端都变 | 两份，同名不同值 |
|---|---|
| 颜色 token | 字号刻度 |
| 品牌（logo、绿、文案语气） | 间距密度 |
| 语义名本身 | 点击区下限 |
| 图标风格、动效曲线 | 组件几何（内距、圆角） |
| 术语表 | 导航范式 |

关键在"语义名本身"这一行：两端都写 `--t-body`，iOS 解析成 16，面板解析成 13。
**代码长得一样，渲染出来是各自的母语。**

为什么不能统一数值：iOS 的 17pt 正文是给 390pt 宽、手持 35cm 定的；侧边栏
360px 在桌面上是另一个观看距离。统一之后面板会像"放大了的手机界面"，而且
跟面板自己的字阶打架。

实现方式——基准写在 `:root`（手机档），面板作用域里重新指派：

```css
:root {                                                   /* 手机 */
  --t-display: 28px; --t-title: 20px; --t-body: 16px; --t-meta: 12px;
}
.panel {                                                  /* Chrome 面板 */
  --t-display: 20px; --t-title: 16px; --t-body: 13px; --t-meta: 11px;
}
```

## 2. 颜色

### 2.1 语义层

| token | 含义 | 用在哪 |
|---|---|---|
| `--ground` | 最底层背景 | 页面底、面板底 |
| `--card` | 浮起的内容面 | 卡片、弹层、输入框 |
| `--inset` | 凹陷面 | 分段控件底、代码块、标题栏 |
| `--hair` | 1px 分隔线 | 行与行之间、卡片描边 |
| `--ink-1` | 主文字 | 标题、强调、唯一加粗的那个字 |
| `--ink-2` | 正文 | 卡片正文、说明 |
| `--ink-3` | 次要信息 | 时间、计数、未选中的导航 |
| `--ink-4` | **装饰，不承载信息** | placeholder、禁用态、空格子 |
| `--accent` | 品牌绿 | 主操作、选中态、热力图 |
| `--overdue` | 警示橙 | 逾期标记。调色板里唯一的警示色，不另造红 |
| `--hl` | 复盘高亮 | 正文里被标记的句子 |
| `--tag-bg` / `--tag-ink` | 标签 | 技术标签、公司标签 |

### 2.2 ink 梯 —— **本次修正**

实测结果：**深色模式全部通过，浅色模式后两档读不出来。**

| | 浅色现值 | 压白卡 | 深色现值 | 压深卡 |
|---|---|---|---|---|
| ink-1 | `#1B231F` | 16.07:1 ✅ | `#E6EEEA` | 14.34:1 ✅ |
| ink-2 | `#6A7670` | 4.73:1 ✅ | `#9AA59F` | 6.66:1 ✅ |
| ink-3 | `#A0AAA5` | **2.39:1 ❌** | `#717A75` | **3.82:1 ⚠️** |
| ink-4 | `#C3CCC7` | **1.64:1 ❌** | `#4B534F` | **2.14:1 ⚠️** |

ink-3 现在装着时间戳、计数、未选中的导航——**那些是信息**，2.39:1 等于没显示。

问题不是单点，是整条梯塌了。浅色的 ink-2 已经贴在 4.5 的地板上（4.73），
下面没有空间再放两档。所以 ink-2 必须上移腾位置。

**修正后：**

| | 浅色 | 压白卡 | 深色 | 压深卡 |
|---|---|---|---|---|
| ink-1 | `#1B231F` 不变 | 16.07:1 | `#E6EEEA` 不变 | 14.34:1 |
| ink-2 | `#525B57` | 7.02:1 | `#9AA59F` 不变 | 6.66:1 |
| ink-3 | `#6D7973` | 4.53:1 | `#78877F` | 4.49:1 |
| ink-4 | `#8C9792` | 3.02:1 | `#5E6A63` | 3.00:1 |

目标值是 **16 / 7 / 4.5 / 3**，不是随手调的：4.5 是正文的无障碍地板，
3 是大字和 UI 元素的地板，7 和 16 往上等距拉开。相邻档之间的对比在
1.48–2.29 之间，都 > 1.3，层级看得出来。

**代价要说清楚**：浅色模式的正文（ink-2）会比现在深一截，和当初照 flomo
量的灰会有偏差。这是必要的——我们的卡片底色和 flomo 不同，同一个灰在
这里压不住。品牌观感和"能不能读"冲突时，后者优先。

**配套规则**：ink-3 是**信息的下限**。任何用户需要读到的字，最淡只能到
ink-3。ink-4 只给装饰用——placeholder、禁用态、空热力格——而且永远不能
是某个意思的唯一载体。

### 2.3 强调色

品牌绿 `#30CF79` 在深色底上 9.23:1，没问题；**在浅底上 1.84:1，几乎看不见**。

所以绿色不是一个值，是三个用途：

| token | 值 | 用途 | 对比 |
|---|---|---|---|
| `--accent` | `#30CF79` | **填充**：按钮底、选中药丸、热力图 | — |
| `--accent-ink` | `#1B231F` | 压在填充上的字 | **7.90:1** ✅ |
| `--accent-text` | 浅色 `#1F874F` / 深色 `#30CF79` | 绿色的**字和图标** | 4.53:1 / 9.23:1 |

**这里推翻了设计稿里的一条旧决定。** 原来绿底配白字，记录在案是"2.03:1，
明知故犯"。实测下来 2.03 不是"将就"，是主操作按钮上的字读不出来。

正确解法不是把绿调暗（那会丢掉品牌色），是**把字翻成深墨**：填充仍然是
一模一样的 `#30CF79`，字色从白换成 `#1B231F`，对比度 2.03 → 7.90。
品牌一个像素没变，可读性从不合格到远超标准。

同理，其余强调色也要分浅深两版：

| | 填充/深底用 | 浅底的字用 |
|---|---|---|
| overdue | `#D97757` | `#C6522D` (4.52:1) |
| gold | `#BFA47A` | `#8F7245` (4.51:1) |
| tag-ink | `#8FA6F0` | `#3A64EB` (4.50:1) |

### 2.4 规则

1. **颜色不能是唯一的信号。** 逾期除了橙色还有 `!` 旗标，新题除了绿条还有 `+`。
   8% 的男性有色觉差异，而且分享卡会被转成灰度。
2. **一个层级最多动两样。** 字号、字重、颜色里挑两个，三样齐动就从"有序"
   变成"吵"。
3. **主题切换只重新指派 token，不重写规则。** 设计稿里 `[data-appearance]`
   就是这么做的——27 条浅色覆盖规则被一次 token 重指派取代。

## 3. 字体

### 3.1 字阶 —— 四档

**这是本文档的核心决定。** 25 档收成**每个平台四档**。

| token | 手机 | 面板 | 用途 |
|---|---|---|---|
| `--t-display` | **28** | **20** | 抽屉大数字、登录页标题 |
| `--t-title` | **20** | **16** | 区块标题、卡片头、行标题 |
| `--t-body` | **16** | **13** | 正文、按钮、绝大多数文字 |
| `--t-meta` | **12** | **11** | 时间、计数、难度、状态、角标 |

四档够用，是因为这个产品的信息层级本来就只有四层：**有多少 → 是什么 →
内容 → 附注**。档位比层级多，多出来的那些必然是"差不多但不一样"，
也就是噪音。那五个 `.5` 小数就是这么来的。

**手机不是 12/14/18/28。** 比例上 12/14/18/28 很干净，但 14 做手机正文
不行：iOS 正文基准是 17pt，flomo 的 memo 正文实测 16，而这个产品的核心
动作就是**在手机上读自己写的题解**。正文压到 14，省下来的是一档字号，
赔进去的是主场景。所以手机从 16 往外推：**28 / 20 / 16 / 12**。

面板同样四档，但基准是 13（桌面惯例，且面板自己已有的字阶就是 13）：
**20 / 16 / 13 / 11**。

两套的比例几乎一致（手机 1.4 / 1.25 / 1.33，面板 1.25 / 1.23 / 1.18），
所以两端看起来是同一个产品，只是一个在手上、一个在桌面上。

**相对单位禁用于字号。** `em` 会让字号依赖 DOM 嵌套深度，同一个组件
放进不同容器就变大小。字号必须是 token，不能是算出来的。

### 3.2 字族 —— 中英双语

产品会有中英两个版本，所以字体不是"一个字体"，是**每个角色 × 两种文字**。

规则只有一条，但它决定一切：**拉丁字族必须排在中文字族前面。** 字体栈
是逐字符解析的——拉丁字母从第一个有该字形的字族取，汉字从第一个有汉字
的字族取。中文字族排在前面的话，它会连拉丁字母一起供给，而中文字体自带
的西文通常很差（SimSun 的英文尤其惨）。

```css
--sans:
  -apple-system, BlinkMacSystemFont,            /* Apple → SF Pro */
  "Segoe UI", Roboto,                           /* Windows / Android */
  "Helvetica Neue", Arial,                      /* 兜底拉丁 */
  "PingFang SC",                                /* Apple 中文 → 苹方 */
  "HarmonyOS Sans SC", "Microsoft YaHei",       /* 鸿蒙 / Windows 中文 */
  "Source Han Sans SC", "Noto Sans CJK SC",     /* Linux 中文 */
  sans-serif;

--serif:
  "Iowan Old Style", Charter,                   /* Apple 拉丁 */
  "Source Serif 4", Georgia, Cambria,           /* 跨平台拉丁 */
  "Songti SC",                                  /* Apple 中文 → 宋体 */
  "Source Han Serif SC", "Noto Serif CJK SC",   /* 思源宋体 */
  SimSun,                                       /* Windows 末位兜底 */
  serif;

--mono:
  ui-monospace, SFMono-Regular, "SF Mono",      /* Apple */
  "Cascadia Code", Consolas,                    /* Windows */
  "JetBrains Mono", "Roboto Mono",              /* 常见安装 */
  Menlo, monospace;
```

角色分工：

| token | 英文落到 | 中文落到 | 用途 |
|---|---|---|---|
| `--sans` | SF Pro / Segoe UI | **苹方 PingFang SC** | 界面。绝大多数文字 |
| `--serif` | Iowan Old Style / Georgia | **宋体 Songti SC** | 登录页标题、成段的话 |
| `--mono` | SF Mono / Cascadia | （不保证等宽） | 代码、题号、设备码 |

衬线只用在"这是一句人话"的地方，不用在界面控件上。中文走宋体是刻意的——
和刷题界面通用的黑体拉开，让登录页读起来像一句话而不是一个系统提示。

### 3.3 中英混排的三个硬差异

同样 16px，实测（macOS / Chrome）：

| | 行盒高 | 单字宽 |
|---|---|---|
| 英文（sans） | 19.0 | 9.02 ≈ 0.56em |
| 中文（sans） | **22.5** | 16.00 = **1.00em** |

**差异一：同字号下中文比英文高 3.5px、宽近一倍。** 汉字占满全角方框，
拉丁字母不占。后果：

- 中英混排的一行里，中文看起来比英文"大一号"。这是正常的，不要靠给中文
  调小字号去补——那会让同一个 token 有两个值，系统就塌了。
- **英文版的留白要重算。** 同一段话，英文占的宽度约是中文的 0.56 倍，
  行数会变少、块会变矮。固定高度的容器在换语言时会露出空当。
  **凡是装文案的盒子一律不写死高度。**

**差异二：行高的需求不同。** 中文需要 1.7–1.8 才透气，英文 1.5 就够。
我们取 **1.7 一个值**：对中文是对的，对英文略松——而这个产品本来就要
"读得下去"的手感，略松是可接受的方向性偏差。

**差异三：字重不对等。** 苹方有 Regular/Medium/Semibold/Bold，但 Windows
的微软雅黑只有 Light/Regular/Bold。所以：

- 中文只用 **400 和 600**。500 在部分平台会被合成（伪中粗），发糊。
- 中文**不用 700**。苹方 Bold 太重，和拉丁 700 不是一个分量。
- 拉丁的 700 只留给衬线 display。

### 3.4 行高

| token | 值 | 用在 |
|---|---|---|
| `--lh-tight` | 1.2 | display —— 大字要紧凑，不然散架 |
| `--lh-snug` | 1.4 | title、meta —— 界面文字要可预测 |
| `--lh-body` | **1.7** | 正文 —— flomo 实测 16/27 = 1.69，也是中文的需求 |

### 3.5 字重

| token | 值 | 拉丁 | 中文 |
|---|---|---|---|
| `--w-regular` | 400 | ✅ | ✅ |
| `--w-medium` | 500 | ✅ | ❌ 可能被合成 |
| `--w-semi` | 600 | ✅ | ✅ |
| `--w-bold` | 700 | 仅衬线 display | ❌ |

不用 300 和 800+：前者在小字号上发虚，后者在界面里永远过重。

一个重要后果：**选中态用 600 会改变文字宽度。** 设计稿里导航每项预留了
固定宽度（`min-width: 30px`），防止"哪一项被选中"改变整条导航的排布。
凡是用字重表示状态的地方都要预留——**中英文都要，英文变宽更明显。**

### 3.6 字距

| 场景 | 拉丁 | 中文 |
|---|---|---|
| 正常文字 | `normal` | `normal` |
| display（≥20px） | `-0.5px` | **`normal`** |
| 全大写小标签 | `+0.09em` | **不适用** |

**字距规则只适用于拉丁。** 负字距收紧的是字母间的视觉缝隙，汉字之间本来
就没有那个缝隙，收紧只会让方块互相挤。正字距同理——`+0.09em` 加在中文上
会变成一排散开的字。

实现方式：带字距的规则挂 `:lang(en)`，或者只挂在确定是拉丁的元素上
（全大写标签、数字）。

### 3.7 规则

1. 字号必须来自 token，不准出现字面量，不准用 `em`/`%`。
2. 拉丁字族排在中文字族前面。
3. 行高跟着用途选，不跟着字号算。
4. 一个层级最多动 {字号, 字重, 颜色} 中的两样。
5. 衬线只用于成段的话，不用于控件。
6. 装文案的盒子不写死高度——换语言会变高矮。

## 4. 间距

4px 栅格。已有且不改：

| token | 值 | 典型用途 |
|---|---|---|
| `--s1` | 4 | 图标和文字之间、标签内距 |
| `--s2` | 8 | 紧凑行内距、按钮组间隙 |
| `--s3` | 12 | 面板里的卡片内距 |
| `--s4` | 16 | 标准块内距、手机卡片间隙 |
| `--s5` | 20 | 面板左右内距 |
| `--s6` | 24 | 手机屏左右内距 |
| `--s7` | 32 | 大区块之间 |
| `--s8` | 40 | 屏级分隔 |

**密度是分平台的**，用同一套 token 的不同档表达：

| | 手机 | 面板 |
|---|---|---|
| 屏/面板左右内距 | `--s6` 24 | `--s5` 20 |
| 卡片内距 | `--s4` 16（登录条目 17，见 §10） | `--s3` 12 |
| 同组元素间隙 | `--s4` 16 | `--s2` 8 |

间距不准出现 token 以外的值。唯一的历史例外是登录条目的 17 和卡片的 17，
来源是 flomo 实测——见 §10 已知偏离。

## 5. 圆角

| token | 值 | 用途 |
|---|---|---|
| `--r1` | 4 | 小药丸、标签、复选框 |
| `--r2` | 8 | 按钮、菜单项 |
| `--r3` | 12 | 面板里的卡片、输入框 |
| `--r4` | 16 | 手机卡片、分享卡 |
| `--r5` | 18 | 大容器 |
| `--rp` | 999 | 胶囊 —— 分段控件、间隔阶梯 |

规律：**容器越大，圆角越大**。嵌套时内层圆角 ≈ 外层 − 内距，否则内外两条
弧对不上，视觉上会"挤"。

## 6. 尺寸与点击区

| | 手机 | 面板 |
|---|---|---|
| 最小点击区 | **44×44pt**（iOS HIG 硬性） | **28×28px** |
| 列表行高 | 40（flomo 实测 40.2） | 36 |
| 标题栏 | 52 | **36** |
| 主按钮高 | 48 | 32 |
| 图标 | 20 | 16 |

**手机的行高 40 低于 44pt 的触控下限，这是故意的。** 视觉密度按 40 画，
可点区域靠 `contentShape` 向外扩到 44 —— 不要为了凑触控下限把行撑高，那会
让整个列表变松。

面板用 28 是因为指针设备的精度远高于手指，桌面 UI 普遍在 24–32 之间。

## 7. 层次

只有两档阴影，没有第三档：

| token | 用途 |
|---|---|
| `--lift` | 轻微浮起 —— 浮在底色上的药丸、图标组 |
| `--shadow` | 真正的浮层 —— 菜单、弹层、分享卡 |

层次优先用**背景色差**（ground / card / inset）表达，阴影是补充。深色模式
下阴影几乎不可见，只靠阴影分层的界面在深色下会糊成一片。

## 8. 动效

| token | 值 |
|---|---|
| `--ease` | `cubic-bezier(.22, .61, .36, 1)` |

时长：进场 420ms（抽屉）、状态切换 180ms、微反馈 120ms。

必须响应 `prefers-reduced-motion: reduce`，把 transition 关掉而不是缩短。

## 9. 迁移表

现有 175 处字号声明按下表归档。**没有四舍五入到看不出的地方**——每一条
都标了会不会改变渲染结果。

### 落地时必须实测的三处

收到四档，代价是**整体字号上浮**，有三个地方会真的挤：

1. **面板的间隔阶梯药丸**（10 → 11）。一行六颗，面板只有 360px 宽。
   必须量，装不下就减少默认档数，不要把字号改回 10。
2. **手机代码块**（13 → 16）。等宽字在 16px 下换行会增多，长代码行要
   确认横向滚动仍然能用。
3. **抽屉署名**（18 → 20）。flomo 实测的 署名÷大数字 = 0.64，改完变成
   20/28 = 0.71，署名会比参考更响。实测后若确实抢戏，这是**唯一**
   值得破例保留 18 的地方——破例就要写进 §10。

## 11. 这些数是怎么来的

方法论，供以后加新值时follow：

- **平台给的**：iOS 正文 17pt、触控 44pt、Web 16px。这些不要自己发明。
- **实测参考**：flomo 的截图逐张标定缩放比后量出来的——28、18、16、
  16/27 的行高、40.2 的行高、12 的计数。量一个你认可的产品再决定抄不抄，
  比"我觉得 24 看起来对"可靠得多，因为对方那个值是真用户用出来的。
- **算出来的**：所有对比度。颜色不靠眼睛判断，浅色模式的 ink-3 看起来
  "挺清楚"，算出来 2.39:1。
- **栅格约束**：间距落 4 的倍数，字号落整数。

没用纯模数音阶（1.2 / 1.25 那种）。比例会给出 20.48 这类数，而屏幕要整数、
行高要落 4px 栅格。实际做法是**比例定方向，手工凑到整数**。

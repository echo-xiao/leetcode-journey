# Chrome 扩展 + GitHub 作为唯一真相源

> **历史设计，已被新规格取代。** 本文保留产品背景和早期决策过程，不再作为当前实施依据。现行行为、架构及 UI 要求统一以 [Leet Jounry 架构与行为规格](../../2026-11-16-leet-jounry-architecture-spec.md) 为准。本文的 FSRS 必填评分、题单来源、旧界面和视觉参数等条款可能已过时。

2026-11-16

## 一句话

把刷题/复习的**执行**搬进一个免费的 Chrome 扩展，把**阅读**留给 iOS app，两端的数据都存在用户自己的私有 GitHub 仓库里——没有服务端，没有 Notion，没有 `content.json`。

## 为什么

现在这套系统只有一台机器能写：我的 Mac，每天 3am 跑一次 launchd。这带来三个问题：

1. **LeetCode cookie 每几周过期一次**，过期后管线不报错，只是返回零道新题。README 里专门写了一段教自己怎么重新贴 cookie。
2. **`content.json` 是个挡在关键路径上的派生产物**。每加一道题整个文件的 hash 就变，条件请求失效，每个用户每天重下整包（414 题 2.3MB，2000 题会到 11MB）。而且"生成了但没推送 = 手机静默拿到陈旧内容、无任何报错"是个已知故障模式。
3. **复习和刷题是断开的**。手机提醒你该复习了，但题要在电脑上做，中间隔着一道手动的坎。

Chrome 扩展同时解掉这三个：它天生带着浏览器里新鲜的 LeetCode 登录态（cookie 问题消失）、它可以直接读写用户的 GitHub 仓库原生结构（`content.json` 可以删掉）、它就长在你做题的那个页面旁边（断裂消失）。

## 范围

**不做的事，以及不做的理由：**

- **不做服务端。** 认证走 GitHub OAuth Device Flow（不需要 client_secret，MV3 后台脚本靠 `host_permissions` 豁免 CORS），数据存用户自己的仓库。
- **先不收费。** 架构上留好位置（见下），但现在零外部用户，定价是在猜。
- **不做通用化。** 只留一个 `domain: "leetcode"` 字段作为将来的抓手，别的一律不抽象。
- **不存 LeetCode 题面。** 只存题号、标题、跳转链接，外加自己用一两句话复述的题意。
- **扩展不做自己的代码编辑器。** 判题只有 LeetCode 能做，扩展是长在它旁边的一层。

## 市场现实

这个赛道有两条需求线，规模差一百倍——这是整份文档里最重要的一组数字。

| 需求线 | 代表产品 | 用户数 | 评分 |
|---|---|---|---|
| **把题解推到 GitHub** | LeetHub v2 | **60,000** | **3.0** |
| 间隔重复复习 | LeetSRS | 684 | 5.0 |
| 间隔重复复习 | Leetcode Anki | 28 | 5.0 |
| 间隔重复复习 | Ankify（未上架，有后端 + AI Coach） | — | — |

**「自动推 GitHub」是一个被六万人验证过的真需求，而且满意度很低（3.0 分 / 87 条评价）。**
不满意的原因能从 fork 谱系读出来：`LeetHub` → `2.0` → `3.0` → `LeetHub AI` → 一堆个人 fork。
这是「读 DOM 的扩展被 LeetCode 改版打死、原作者维护不动、社区不断接盘」的典型形态。
LeetHub 3.0 的修复方式恰好是改成从 GraphQL 拉真实提交——和本设计的选择一致。

**定位因此改写：不是再做一个复习扩展去挤那 684 个用户的市场，而是——**

> LeetHub 把你的题解推上 GitHub 然后就不管了。我们让那个仓库活起来。

入口用大需求（自动推 GitHub），留存用小需求（复习调度）。先满足大的再用小的留人，
比反过来容易得多。

差异化与竞品正交：
- 竞品把数据存在自己的数据库或 Gist 里（黑盒存档）；这里的用户仓库**本身就是人类可读的题解库**。
- 没有竞品做移动端。
- 没有竞品用 Device Flow——他们要么让用户手贴 PAT，要么让用户自己去 GitHub 建 OAuth App 填
  client secret，要么自建后端存 secret。认证体验是现成的真空。
- Ankify 赌 AI 生成，这里赌个人沉淀——AI 只给草稿，**永远不碰用户写的文件**。

## 系统边界与两端职责

```
         ┌──────────────── Chrome 扩展（免费 · 写端）─────────────────┐
         │  · 今天做哪些题 → 跳转 LeetCode                            │
         │  · AC 后评分（Again/Hard/Good/Easy）                       │
         │  · 写题解回仓库                                            │
         │  · 唯一的调度器（FSRS 只在这里跑）                          │
         └───────────┬──────────────────────┬─────────────────────────┘
          读 leetcode.com/graphql        读写（Device Flow · write）
          （带浏览器天然登录态）                 │
                                                ▼
                              ┌─────────────────────────────────┐
                              │  用户的私有 GitHub 仓库           │
                              │  = 唯一真相源                    │
                              └─────────────────┬───────────────┘
                                                │ 只读（Device Flow · read）
         ┌──────────────── iOS App（纯读）──────┴─────────────────────┐
         │  · 抽屉首页：三个大数字、热力图、今天的进度、三维度列表       │
         │  · 阅读：题意 → 伪代码 → 题解 → 我的代码（逐层展开）             │
         │  · 推送提醒                                                │
         │  · 提交热力图（直连 leetcode.com/graphql，绕过仓库）          │
         │  不评分、不调度、不写入                                      │
         └────────────────────────────────────────────────────────────┘
```

**为什么扩展必须有三件事而不能只有"今天几题"：** app 是纯读的，不给分；如果扩展也不给分，FSRS 就没有输入，下次复习时间算不出来，调度器是死的。而且评分的时机只可能是刚 AC 完的那一秒——晚上掏手机回忆"今天那题顺不顺"，分不准。

**接受的代价：** 手机上翻过的题不计入调度。这是"app 纯读"换来的——系统里只有一个调度器，不会出现两个答案打架、而你不知道该信哪个。

## 用户仓库长什么样

沿用现在 `Problems/` 的结构，一题一文件夹。**没有 `content.json`。**

```
0104-maximum-depth-of-binary-tree/
  meta.json        题号、标题、难度、technique 标签、LeetCode 链接、due 日期
  prompt.md        题意：这道题在问什么（自己复述，一两句，不是 LeetCode 原文）
  pseudocode.md    整体思路、伪代码、复杂度
  review.md        题解 —— 界面上叫「题解」，文件名沿用 review.md。带 ==橙色高亮==
  draft.ai.md      AI 草稿 —— 可随时重新生成、随便覆盖
  solution_*.py    每一版 AC 的代码
reviews/
  2026-11.jsonl    append-only 评分日志
```

**复习链条是四层，每一层都是用户自己写的：**

```
① 题意      这道题在问什么——知道问什么，但不含任何解法
② 伪代码    结构层面的提示
③ 题解      完整的思路 + 当时卡在哪，带橙色高亮
④ 我的代码  每一版 AC
```

**界面上这一层叫「题解」，文件仍是 `review.md`。** 不存在单独的题解文件——原来的「复盘」写的
本来就是"这题该怎么想、我当时怎么卡的"，那就是题解。再开一个文件只会让同一件事分裂成两处。
文件名不改，省掉一次无意义的迁移。

**题意（`prompt.md`）是题面的替身。** 它同时解决三件事：版权干净（是自己的复述，不是 LeetCode
的表达）、离线可用（不依赖打开 leetcode.com）、而且**复述题意本身就是理解的检验**——一道题
如果没法用一句话说清它在问什么，基本等于没懂。

**原来的"一句话直击本质"去掉。** 那是 AI 生成的解法摘要，价值不足以占一层——而且它写的是答案，
放在第一屏会当场毁掉回忆的机会。`pseudocode.md` 保留整体思路、伪代码、复杂度。

`elements.md` 也不再是独立文件——手写的要素内容并入 `review.md`（界面上的「题解」），自动生成的要素答案不再产出。

至此 **AI 生成的内容在复习链条里一样不剩**，只有一个用户主动点才生成、写在 `*.ai.md` 里、
代码层面碰不到用户文件的草稿。

**目录命名对齐 LeetHub**：零填充四位题号 + 连字符 + slug，放仓库根目录（原来是
`Problems/104_maximum-depth-of-binary-tree`）。代价是一个迁移脚本跑一遍 414 个文件夹，
买到的是和六万人既有习惯的一致性，以及下面说的共存能力。

**不存题面。** 扩展不写题面文件；迁移时现有的 `problem.md` 不进新结构，app 不读、不打包。
（LeetHub 把题面写在每题的 `README.md` 里，那是它写进用户自己仓库的，我们同样不读不分发。
用户仓库里有什么是用户自己的事，我们只对自己写出去的内容负责。）
系统里 100% 是用户自己的创作（题意、伪代码、题解、代码），法律上干净。app 里再放一个
「在 LeetCode 打开」的链接兜底——想看原题随时跳过去，我们只是不存它。

**`domain: "leetcode"` 写在 `meta.json` 里**，是唯一的通用化抓手。成本接近零，不留的话将来老数据没办法区分领域。其余一概不抽象——现在连第二个领域的影子都没有，照着想象中的用例抽象，抽出来的八成是错的。

### 和 LeetHub 共存

LeetHub 生成的结构是本设计的子集：

```
0001-two-sum/
  0001-two-sum.py   ← 代码
  README.md         ← 题面
```

所以兼容是**不对称的两件事**：

- **读兼容（必做）**：能认出一个已有的 LeetHub 仓库并接管——只取题号、标题、代码，
  不碰 `README.md`。一个用了两年 LeetHub 的人装上就有几百道题的数据，零成本冷启动。
- **写兼容（建议做）**：命名对齐之后，两个扩展可以**同时往一个仓库里写而不打架**。
  LeetHub 继续写代码和题面，我们在旁边写 `prompt.md` / `pseudocode.md` / `review.md` /
  `meta.json`。不替代它，长在它旁边——不要求用户放弃已有的工具和仓库。

**pattern 只当标签。** `technique: "binary-tree"` 用于分组和"今天只复习二叉树"。原先 `element_essentials.py` 里"每个 pattern 有哪几个空"那套定义删掉——自动生成的要素答案没有价值，手写的要素并进题解。

## 读写协议

### 读：Git Trees API + blob SHA 增量

```
启动 → GET /repos/{owner}/{repo}/git/trees/{sha}?recursive=1
     → 拿到全树 + 每个文件的 blob SHA
     → 与本地缓存的 SHA 比对
     → 只拉 SHA 变了的文件（通常 0~3 个）
```

这是白嫖 git 的内容寻址当缓存键：不用版本号、不用 diff 逻辑、不用 ETag，git 已经精确算好了"什么变了"。上限是 10 万个文件 / 7MB，2000 题 × 5 文件 = 1 万条，远没到顶。

**冷启动走懒加载**：首次只拉 index（题号/标题/难度/due），点进某题才拉正文。一天翻 5 道题，没理由先把 2000 道的正文全下下来。

### 写：只有扩展，带本地队列

写入失败（没网、token 过期、API 限流、在飞机上）时进 `chrome.storage` 队列，联网自动补推。**写端丢数据不可接受**——队列防的主要不是 GitHub 宕机（一年一次），是前面那四种（一周一次）。

### 认证：GitHub Device Flow

```
扩展/app 显示：请在浏览器打开 github.com/login/device，输入 WDJB-MJHT
用户授权 → 后台轮询 → 拿到 token
```

不需要 client_secret，不需要服务端。扩展申请 write 权限，app 只申请 **read** 权限——用户授权时看到"只读"，信任感完全不同。

首次使用时扩展用 GitHub API 在用户账号下创建一个**纯数据私有仓库**（只有数据，没有任何代码）。数据和代码彻底分离：用户的仓库永远不需要"更新"，产品升级就是扩展自动更新，零迁移成本。

## 调度

FSRS 只跑在扩展里，用现成的 `ts-fsrs` 库（竞品 Ankify 在用，FSRS-6），**不手写移植**。现有的 `app/ios/LCReviewTests/Fixtures/fsrs-baseline.json` 留下来，用于验证库的输出与原 Swift 实现一致。

扩展把每题算出的 `due` 日期写进 `meta.json`；app 只读日期排本地通知，自身不含任何调度逻辑。

评分写成 **append-only 日志**（`reviews/YYYY-MM.jsonl`），不是可变状态文件。好处：历史永不损坏，将来换 FSRS 参数或算法只要重放日志。当前只有一个写者（扩展），所以不需要合并逻辑——但格式本身为将来留了门。

## 题单：从「记录你刷了什么」到「告诉你刷什么」

现在整套系统是被动的：你在 LeetCode 上刷了什么，管线就记录什么。「基于题单做新题」是主动的
——它要决定下一道该做哪个。这是一个和复习并列的新模式，所以扩展的「今天」分成两半。

**没有「启用题单」这个动作。** 题单就是一串题号，你做过哪些是已知的，所以**任何题单的进度在
任何时候都能直接算出来**——Blind 75 做了 38 道这件事，不需要先「启用」它才成立。

唯一的设置是 **「主线是哪一个」**，它决定新题按谁的顺序出，只能有一个，也可以选「不要新题，
只复习」。这一个决定删掉了一整类状态：没有「启用了但没进度」「启用后又停用」「启用了三个该听谁的」。

| 题单来源 | 怎么拿到 | 改题单要动代码吗 |
|---|---|---|
| LC 官方学习计划（Top Interview 150、LeetCode 75、Top 100 Liked、二分、DP、图论） | LeetCode GraphQL 直接查 | 不用 |
| NeetCode 150 / Blind 75 / Grind 75 | 不在 LeetCode 上，是第三方清单；本质是一组题号，打包成静态 JSON 随扩展分发 | 要，发版时更新 |
| 用户在 LC 上的收藏夹 | favorites V2 GraphQL，需要登录态——扩展天生就有 | 不用，在 LeetCode 上改完即生效 |
| 仓库里自定义 | `lists/my-plan.json`，纯题号数组，完全不依赖 LeetCode | 不用，改文件即可 |

**优先级规则：复习永远排在新题前面。** 逾期的旧题先清，清完才给新题。否则会出现「一边欠着
40 道没复习、一边继续往前推新题」——那正是这套系统存在的理由要解决的问题。换主线只影响
「新题」那一格，复习那部分跟题单无关。

这一节同时填上了 `problemSetSection` 那个一直空着的坑。它的 `unavailable` 文案写的是
`"no list membership yet (LC75, Top 100)"`——当时拿不到题单数据，是因为管线跑在 Mac 上没有
登录态。扩展一来这个限制就没了。这是扩展带来的第三个红利（前两个是 cookie 不再过期、
`content.json` 可以删）。

## 目标设定在扩展，不在 app

**这不是偏好，是架构定的：app 只申请 read 权限，写不了任何东西。** 任何会改变调度行为的设置，
只能放在能写的那一端。

| | 在哪设 | 在哪看 |
|---|---|---|
| 每天给几道新题 | 扩展 · 设置 | 两端 |
| 每日复习上限 | 扩展 · 设置 | 两端 |
| 主线题单 | 扩展 · 设置 | 两端 |
| Claude API key（BYOK） | 扩展 · 设置 | — |
| 今天 N 题 / 已完成 M 题 | —（算出来的） | app 首页 + 扩展「今天」 |

**扩展设目标，app 当记分牌。** 代价是人在手机上改不了目标，得回电脑——可以接受，目标不是每天
调的东西，而且刷题本来就发生在电脑前。

## 扩展 UI

**形态：Chrome MV3 Side Panel，不往 LeetCode 页面注入 DOM。**

两个理由，第二个比第一个重要：

1. 注入 DOM 要猜 LeetCode 的 HTML 结构，人家一改版就瞎——LeetHub 被 fork 四次就是这么来的，
   而 LeetHub 3.0 的修复方式正是改成从 GraphQL 拉真实提交。
2. **popup 点一下别处就关了**（flomo 的扩展就是 popup）。side panel 一直开着、跟着你换题自动
   更新，这才撑得住「做题全程它都在」。

**面板自己随处境切换，不是三个页面。** 打开某道题的页面 → 自动切到「这道题」；AC 被检测到 →
评分自动弹出；跳到下一题 → 内容跟着换。底部三个 tab（`今天 / 这道题 / 设置`）只是手动兜底，
正常流程里一次都不用点。

四个状态：

```
① 今天      复习（逾期在前）+ 分隔线 + 新题（主线题单的下一道，显示「第 42 / 150」）
② 做题中    题号标题 + technique pill（题面就在你眼前的页面上，面板不重复它）
            ▸ 想不起来？看伪代码        ← 默认折叠，第 1 层
            ▸ 还是卡住？看上次的题解    ← 第 2 层
③ AC 后     [Again][Hard][Good][Easy] + 下次复习日期 + 「更新我的题解」+ 保存
④ 设置      GitHub 连接 / 每天的目标 / AI 草稿 key
```

**视觉沿用 flomo 扩展的语言**：标题栏左侧 logo + 名字、右侧**状态点**（绿「已同步」/
橙「3 条待推送」），内容区，底部三 tab，主按钮绿色实心。

**降级态要明说，不能装没事。** 没网、token 过期、LeetCode 掉登录——状态点变色，正文下方出一条
可操作的琥珀条（`⚠ 没网，3 条记录排队中 · 重试`）。数据进本地队列不会丢，但必须让人看见它还
没推上去。

**「看上次题解」默认折叠是整个产品的灵魂**——一打开就看见答案，间隔重复就失效了。分两层是因为
伪代码和题解是不同深度的提示，**记录你停在哪一层**，比只记「看没看答案」信息量大得多。

## App 改造

视觉设计和阅读交互 **100% 保留现有设计**，砍掉的只是评分流程那一层。

| 组件 | 处理 |
|---|---|
| `Theme.swift` | 保留。flomo 风格、teal 单色，与交互无关 |
| `ChainCardView` | 保留。串珠卡片：题意 → 伪代码 → 题解 → 我的代码，一层一张卡，虚线相连 |
| `HeatmapView` | 保留 |
| `HighlightedText` | 保留。渲染题解里的 `==橙色高亮==` |
| `HomeView` | 改造成抽屉，见下 |
| `SessionView` / `GradeBar` | 删除。session 是评分流程的容器 |
| `Grading` / `SessionRunner` / `SessionBuilder` / `FSRS.swift` | 删除 |
| `SettingsView` 的 session 长度 | 删除。app 唯一那个旋钮随 session 一起消失 |
| `ContentStore` | 改造：读路径从匿名 Raw 换成带 token 的 GitHub API + Trees/SHA 增量 |

### 首页是一个抽屉

和 flomo 手机版一样——**首页不是独立页面，是盖在阅读页上的一层**：

```
平时看到的是阅读页 → 点左上角 ☰ → 抽屉从左侧滑出，占 79% 屏宽，
右边留一条缝露出底下内容 → 选一个分类，抽屉自动收回，屏幕上剩下那一类的题
```

抽屉内容，自上而下，**全程没有卡片**：

```
☰  Echo                    🔔 ⚙
 414        18        12
 题         类        连续          ← 三个大数字均分铺开，小标签在下
[热力图 12 列 · 今天那格描边不填充]
9月    10月    11月
今天 7 题 · 已完成 3
▬▬▬▬▬░░░░░░░
题单  分类  时间                    ← 轻量文字切换，选中项加一道绿下划线
# 二叉树              5/61
    # 遍历            2/28          ← 子项缩进
    # 构造            3/19
# 滑动窗口            8/42
```

每行右边是 **`待复习 / 总数`**（沿用现有 `HomeEntry` 的 backlog / total），不是进度条——
绿色那个是现在等着你的，灰色是这一类一共有多少。

动画：三层（阅读层 / 蒙层 / 抽屉）用**同一条曲线、同一个时长**
（`.42s cubic-bezier(.22,.61,.36,1)`，快出慢入），所以是一个动作而不是三个动画各跑各的。
**只过渡 `transform` 和 `opacity`**——不要碰 `filter`，它每帧强制重绘整层，会直接拖垮帧率。
`prefers-reduced-motion` 下全部关掉。

### 阅读：卡片是点出来的，不是折叠的

下一张卡在点之前**并不存在**——这是 `ChainCardView` 原本的机制（`opened as far as revealed`）。
所以屏幕上永远没有灰着的「轻点展开」占位行。

**题解不设门槛。** 折叠的意义是先逼你回忆、再给答案；但这一层不只是答案，它还记着你当时卡在哪——
没有「回忆它」这回事，藏起来只是多一次点击，而它恰恰是打开 app 想看的东西。

### 降级

断网时用本地缓存，顶部标注「数据截至 X 月 X 日」——沿用热力图现有策略。两条不同的消息
（「有缓存但旧」vs「从未成功过」）要分开，因为把两者都画成空白会让「没数据」读起来像「没练习」。

## AI 草稿

**按需生成，不自动生成。** AC 后自动生成会产生大量永远不看的草稿，还白烧 token（BYOK 的话是烧用户的钱）。

**保证"不覆盖用户内容"的方式是权限隔离，不是小心。** 生成逻辑在代码层面只能写 `*.ai.md`，碰不到 `review.md`。想把草稿收进自己的题解靠手动复制——这个"手动"不是麻烦，是真正读了一遍的证据。

Claude 调用走 BYOK。绝大多数用户永远不会触发。

## 迁移步骤

1. **新建 `echo-xiao/lc-data` 私有仓库**，把 414 道题的 `Problems/` 搬过去。原仓库只留产品代码。
   成为自己产品的第一个用户——用真实数据跑通授权、冷启动、懒加载，比用假数据强得多。
2. **转换文件结构**：拆出 `meta.json`；`elements.md` 并入 `review.md`；丢弃
   `pseudocode.md` 里的"一句话直击本质"那一条。
3. **补 `prompt.md`**：用 AI 从现有的 `problem.md` 各生成一句题意草稿，之后随手改。
   **这是 `problem.md` 这辈子最后一次有用**——跑完就连同 `fupan.py` 一起删。
3. **删除 Notion 整条链路。** 历史复盘已经在仓库里了（414 道题中 326 道的 `review.md` 非空，其中 109 个带 `==高亮==`），不需要再导出。
4. 建扩展，接上 Device Flow 和 Trees API 读路径。
5. 改 iOS app。

## 风险与未决

- **市场很小。** 最大的竞品 684 个用户。这个项目的现实定位更接近自用工具 + 作品集，而不是生意。
- **依赖 LeetCode 的非公开 GraphQL。** 它变了，采集就断。现在已经是这样，扩展不改变这一点，但扩展的失败会更早被发现（实时 vs 第二天）。
- **商业化留位但不实现。** 将来要收费，收敛成扩展/app 里一个独立模块，接口 `verify(key) -> Entitlement`。走 App Store **买断**（参照 AnkiMobile $24.99），不做订阅——没有持续服务端成本，收不出订阅的正当性。Chrome Web Store 自己的支付系统已于 2021 年 2 月彻底关停，扩展侧没有收费通道，这也是扩展保持免费的现实原因之一。
- **还没画的屏：** 空状态、首次 Device Flow 授权流程、更细的错误态。骨架和规范已定，这些留到实现期。
- **预生成 elements 答案库不做。** 等有真实用户再说。
